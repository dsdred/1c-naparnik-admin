# Issue #1: готовый ответ теряется при блокировке SQLite

Ишью: https://github.com/dsdred/1c-naparnik-admin/issues/1

Ветка: `codex/fix-issue-1-sqlite-busy`.

## Проблема

После получения готового ответа от Напарника шлюз сохранял контрольную точку
истории и привязку сессии. При блокировке SQLite обе записи последовательно
ждали освобождения базы, а ошибка `SaveSession` возвращалась клиенту вместо
готового ответа. Регрессионный тест воспроизвёл `SQLITE_BUSY` и задержку
около 10 секунд на исходном коде.

## Решение и выполненные изменения

- Привязка сессии сохраняется первой. Ошибка этой записи оставляет готовый
  ответ доступным клиенту и регистрируется как предупреждение.
- После неудачного сохранения сессии запись контрольной точки пропускается,
  чтобы повторно не ждать ту же блокировку SQLite.
- Ошибка сохранения контрольной точки также регистрируется как предупреждение
  и не заменяет готовый ответ ошибкой.
- Движок использует журнал приложения, включая файл журнала службы Windows;
  при отсутствии явно заданного журнала используется стандартный `slog`.
- Добавлен тест с временной SQLite и локальным имитатором API Напарника.
  Он проверяет возврат ответа при блокировке, одно предупреждение без повторного
  ожидания, успешное сохранение обеих записей после снятия блокировки и отдельный
  сбой контрольной точки, искусственно вызванный триггером SQLite.
- Добавлена запись в историю изменений.

Ожидание первой записи ограничивается существующим `busy_timeout` SQLite
(5 секунд). Если служебное состояние не сохранилось, следующий запрос с полной
историей может создать новый диалог Напарника.

## Изменённые файлы

- `internal/gateway/engine.go` — обработка ошибок сохранения и предупреждения.
- `internal/app/app.go` — передача журнала приложения движку.
- `internal/gateway/engine_sqlite_test.go` — регрессионная проверка.
- `CHANGELOG.md` — описание исправления в разделе `Unreleased`.
- `docs/issues/1-sqlite-busy.md` — этот файл с описанием ишью и решения.

## Проверка

На Windows amd64, Go 1.27.4:

- До исправления регрессионный тест падал с `SQLITE_BUSY` примерно через 10 секунд.
- После исправления тест проходит примерно за 5 секунд.
- `go test ./...` — успешно.
- `go vet ./...` — успешно.
