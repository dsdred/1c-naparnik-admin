# Протокол проверки публичного API «1С:Напарник разработчика»

**Дата:** 25.11.2026
**Базовый адрес:** `https://code.1c.ai`
**Тариф:** активен (проверено через `/budget`, ошибки `no_active_tariff` нет)
**Окружение:** curl 8.x (Git Bash, Windows)

Все запросы выполнены на тестовом диалоге, созданном специально для проверки. После теста диалог удалён (`DELETE` → 204, список пуст).

## 2. Стоимость в лимитах

После четырёх обращений к модели (два обычных сообщения, вызов инструмента, результат инструмента) плюс `no_generate`:

```
GET /budget → sliding_5h.used_percent = 0.0, weekly.used_percent = 0.0
```

То есть **одна операция стоит меньше 0.05% недельного лимита** — процент отдаётся с точностью до 0.1 и просто не «шевелится» на такой выборке. Вывод: на уровне «Базовый» счёт идёт не на десятки запросов, а на сотни/тысячи; узким местом скорее станет 5-часовое окно при пакетной обработке, чем общий объём.

Фактический расход токенов из поля `usage` (недокументированное, но приходит):

| Операция | prompt | cached | completion | reasoning | total |
|---|---|---|---|---|---|
| 1-е сообщение (пустой диалог) | 5371 | 5184 | 155 | 27 | 5526 |
| 2-е сообщение (контекст 1 хода) | 5756 | 5504 | 61 | 0 | 5817 |
| сообщение с инструментом | 5097 | 1664 | 231 | 193 | 5328 |
| результат инструмента | 5353 | 1664 | 71 | 0 | 5424 |

Важное следствие: **системный промпт агента ≈ 5 тыс. токенов и почти весь кэшируется**. Стоимость одного запроса определяется не вашим вопросом, а этим фиксированным префиксом — поэтому «мелкие» вопросы стоят почти столько же, сколько крупные.

`context_tokens` после двух ходов: `token_count: 5817` — совпадает с `total_tokens` последнего ответа.

## 3. Расхождения с документацией

1. **`max_context_length` = 384000**, а не 128000 из примера в доке. Пример был иллюстративным, но фактическое значение стоит знать: контекст втрое больше ожидаемого.
2. **`PUT /title` возвращает `204 No Content`**, а не JSON — в доке код ответа не указан. Клиенту не нужно парсить тело.
3. **`422` отдаёт `error` массивом**, а не строкой:
   ```json
   {"error":[{"type":"literal_error","loc":["body","role"],"msg":"Input should be <MessageRole.USER: 'user'> or <MessageRole.TOOL: 'tool'>","input":"robot","ctx":{...}}],"error_type":"validation"}
   ```
   Формат `error` описан как «строка или объект» — фактически бывает и массив (стиль FastAPI/pydantic).
4. **В пакетах SSE есть недокументированные поля**: `type` (`chat_skill_user` / `chat_assistant`), `details` (`finish_reason`, `max_context_length`, `task_id`, `source`, `source_run_uuid`, `format_valid`), `diagnostics` (`reanchored`, `anchor`, `branch_tail`, `replay`, `ignored_tool_call_ids`, `task_closed`), `usage`.
5. **`tool_calls[]` содержит дополнительное поле `type: "function"`** и в дельтах приходит с `index` — как и предупреждает документация, `arguments` собирается накоплением.
6. **`last_activity` в списке диалогов не обновился** после четырёх сообщений — остался равен `create_time`. Либо обновляется с задержкой/по другому событию, либо это баг беты. Сортировку списка на этом строить рискованно.

## 4. Практические грабли

### Кириллица в теле запроса на Windows

Первый же `POST .../messages` вернул:

```
HTTP 400 {"detail":"There was an error parsing the body"}
```

Причина — не API, а консоль: Git Bash/Windows передал русский текст в cp1251, тело перестало быть валидным UTF-8. Лечится записью тела в файл и `--data-binary @file`. **В коллекции Bruno этой проблемы нет** (там UTF-8 изначально), но для скриптов на PowerShell/CMD это грабли №1: используйте `[System.Text.Encoding]::UTF8.GetBytes(...)` или файл.

### Семантика потока подтвердилась

- Первый пакет — эхо пользовательского сообщения: `role: user`, `content: null`, `finished: true`, уже с присвоенным `uuid`.
- Далее пакеты с тем же `uuid` ассистента, `role: null`, `finished: false`, заполнен `content_delta` (в том числе пустые пакеты — норма).
- Финальный пакет: `role: assistant`, `finished: true`, полный `content` + `reasoning_content` + `usage`.
- При ответе на `role: tool` в потоке **два** текстовых пакета ассистента (промежуточный «Версия конфигурации: 3.0.123.45» и финальный развёрнутый) — подтверждает предупреждение, что ответов ассистента может быть несколько.

### Коды ошибок совпали с докой

| Запрос | Ответ |
|---|---|
| без заголовка | `401 {"error":"No token provided","error_type":"no_token"}` |
| с мусорным ключом | `401 {"error":"Token not found","error_type":"token_not_found"}` |
| несуществующий диалог | `404 {"error":"Conversation with uuid ... not found","error_type":"resource_not_found"}` |
| `role: "robot"` | `422 validation` (см. п. 3.3) |

Обратите внимание: невалидный ключ даёт `token_not_found`, а не `invalid_token` — при обработке ошибок ориентируйтесь на `401` в целом, а не на конкретный `error_type`.

### Окно лимитов

`weekly.resets_at` = `2026-11-29T22:57:27Z` — это **не календарная неделя**, а скользящие 7 суток от момента активации ключа. Планировать «сброс в понедельник» нельзя.

## 5. Параллельные запросы, компактизация и `409`

`409 conflict` документация описывает как «несовместимое состояние (например, генерация уже идёт)». Воспроизвести не удалось — три сценария, все прошли без конфликта:

| Сценарий | Результат |
|---|---|
| Два `POST /messages` с `parent_uuid: null` одновременно | оба 200, в диалоге две ветки |
| Два `POST /messages` с **одним и тем же** `parent_uuid` одновременно | оба 200, две ветки от одного родителя |
| `POST /compact` во время генерации ответа | 200, `compact_finished` |
| `POST /title` во время генерации ответа | 200, название сгенерировано |

Выводы для клиента:

- **Сервер не блокирует диалог на время генерации** — параллельные сообщения создают ветки, а не конфликт. Значит `GET /conversations/{uuid}` (плоский список без ветвления) после такого «разветвления» покажет сообщения всех веток подряд, и восстановить по ним линейную историю нельзя. Если ветвление не нужно — сериализуйте запросы на своей стороне.
- **Компактизация на коротком контексте — no-op**: на диалоге в ~6 тыс. токенов `compact` мгновенно вернул `compact_finished`, ничего не сжав. Полезный эффект начинается только у `max_context_length`, то есть ближе к 384 тыс. токенов.
- `compact` во время генерации не ломает текущий ответ (сам ответ дошёл полностью, 10.4 с).
- **Один раз из шести** параллельных запросов curl получил обрыв без HTTP-ответа (`000`, 21 с) — второй запрос при этом прошёл штатно. Повторить не удалось, похоже на сетевой сбой, но для конвейера вывод практичный: нужен ретрай на транспортные ошибки, а не только на 5xx.

## 6. Что стоит поправить в коллекции Bruno

- Добавить в `docs` запросов замечание про `--data-binary @file` для не-Windows-инструментов.
- Для `PUT /title` тест ожидает `204`, а не `200`.
- `GET /budget` в тестах не должен падать на `used_percent: 0.0` — проверять наличие блока `limits`, а не значение.
