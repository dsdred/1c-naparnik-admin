# 1С:Напарник разработчика — публичный API (бета)

Справочник составлен по официальной документации <https://code.1c.ai/public-api/> (снято 25.11.2026, статус — бета-версия с 01.12.2026).

- Базовый адрес: `https://code.1c.ai`
- Все пути ниже — относительно базового адреса
- Транспорт: HTTPS, дополнительное ПО не требуется
- Ключи доступа: <https://code.1c.ai> (раздел «Ключи доступа») или <https://portal.1c.ru>
- Поддержка: ailab@1c.ru (по вопросам API), support@1c.ai (по продукту)

---

## 1. Аутентификация

Единственный способ — заголовок с API-ключом:

```http
Authorization: Bearer <api_key>
```

Ключ привязан к пользователю (лицензии тарифицируются по ключам). При компрометации ключ перевыпускается в личном кабинете.

## 2. Эндпоинты

### 2.1. Управление диалогами

#### POST `/public/v1/conversations` — создание диалога

Вызывается перед отправкой первого сообщения.

Запрос:

```json
{
  "ui_language": "ru",
  "programming_language": "1c",
  "script_language": "ru",
  "title": null
}
```

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `ui_language` | `"ru"` \| `"en"` | нет | Язык интерфейса, по умолчанию `ru` |
| `programming_language` | `"1c"` \| `"java"` \| ... | нет | Язык разработки, по умолчанию `1c` |
| `script_language` | `"ru"` \| `"en"` | нет | Язык комментариев к коду |
| `title` | string \| null | нет | Название диалога; `null` — без названия |

Ответ:

```json
{
  "uuid": "3f2b...",
  "create_time": "2026-08-25T10:00:00Z"
}
```

#### GET `/public/v1/conversations` — список диалогов

Query-параметры:

| Параметр | Описание |
|---|---|
| `limit` | 1–100, по умолчанию 10 |
| `offset` | ≥ 0 |

Сортировка — по `last_activity`, сначала недавно активные.

```json
{
  "conversations": [
    {
      "uuid": "3f2b...",
      "skill_name": "public_api",
      "title": "Объяснение функции X",
      "create_time": "2026-08-25T10:00:00Z",
      "last_activity": "2026-08-25T10:00:00Z"
    }
  ]
}
```

`title` может быть `null`, если не задано.

#### GET `/public/v1/conversations/{conversation_uuid}` — информация о диалоге

Возвращает основные сообщения (пользователь, ассистент, результаты инструментов — без служебных), отсортированные по времени, единым плоским списком **без ветвления**.

```json
{
  "uuid": "3f2b...",
  "create_time": "2026-08-25T10:00:00Z",
  "skill_name": "public_api",
  "title": "Объяснение функции X",
  "details": {
    "ui_language": "ru",
    "script_language": "ru",
    "programming_language": "1c"
  },
  "messages": []
}
```

Элемент `messages` — `ConversationMessage` (см. раздел 3).

#### DELETE `/public/v1/conversations/{conversation_uuid}` — удаление

Ответ: `204 No Content`.

### 2.2. Названия диалогов

#### POST `/public/v1/conversations/{conversation_uuid}/title` — генерация названия

Вызывается **после** генерации первого ответа ассистента. Сервер генерирует название по содержимому диалога.

- Первый вызов — генерация.
- Последующие вызовы возвращают уже сохранённое название.
- Если информации недостаточно — `424 insufficient_context` (повторить после новых сообщений).

Тело запроса пустое. Ответ:

```json
{ "title": "Объяснение функции X" }
```

#### PUT `/public/v1/conversations/{conversation_uuid}/title` — изменение названия

```json
{ "title": "Моё название" }
```

Ответ: `204 No Content` (проверено на живом API 25.11.2026 — в документации код не указан).

### 2.3. Компактизация контекста

Компактизация — механизм сжатия длинного контекста. Два режима:

- **Авто-компактизация (серверная)** — запускается автоматически при приближении к `max_context_length`, клиентом не управляется.
- **Управляемая компактизация** — клиент явно инициирует сжатие.

#### POST `/public/v1/conversations/{conversation_uuid}/compact`

Синхронно запускает компактизацию и ждёт завершения.

```json
{ "instruction": "" }
```

`instruction` — необязательные требования к сжатию на естественном языке.

Ответ:

```json
{
  "success": true,
  "result": { "status": "compact_finished" }
}
```

`status`: `compact_finished` | `compact_limited`.

### 2.4. Сообщения (стриминг)

#### POST `/public/v1/conversations/{conversation_uuid}/messages`

Заголовок `Accept: text/event-stream`. Ответ — SSE-поток.

Запрос:

```json
{
  "parent_uuid": null,
  "role": "user",
  "content": "Какая сегодня погода?",
  "tools": [],
  "no_generate": false
}
```

| Поле | Описание |
|---|---|
| `parent_uuid` | uuid сообщения-родителя; `null` для первого |
| `role` | `user` \| `tool` |
| `content` | для `user` — строка; для `tool` — список `ToolContent` |
| `tools` | список `ClientTool`, только при `role: user` |
| `no_generate` | сохранить сообщение без генерации ответа |

Пакет ответа:

```json
{
  "uuid": "msg-2",
  "parent_uuid": "msg-1",
  "role": "assistant",
  "content": {},
  "content_delta": {},
  "finished": false
}
```

В пакетах могут быть дополнительные поля (`type`, `details` и др.) — клиент обязан опираться на документированные поля и игнорировать неизвестные.

**Семантика стриминга:**

1. Первый пакет — **эхо** пользовательского сообщения: `role`/`parent_uuid` из запроса, `content` и `content_delta` = `null`, `finished: true`. Даёт клиенту `uuid` отправленного сообщения.
2. Для `role: tool` первые пакеты — подтверждения сохранённых tool-сообщений (по одному на `tool_call_id`).
3. Сообщения ассистента приходят **дельтами** (`finished: false`, заполнен `content_delta`), затем финальный пакет (`finished: true`, заполнен `content`).
4. **Финальный `content` приоритетнее** накопленных дельт — сервер мог отфильтровать/скорректировать текст.
5. Ответ может содержать несколько сообщений ассистента (сообщение → вызов инструмента → следующее сообщение).
6. Пока серверный инструмент выполняется, может прийти служебный пакет прогресса: `finished: false`, `content: null`, `uuid: ""`, `content_delta` с `tool_call_id` и `name`. Сообщения с пустым `uuid` в истории нет — это только индикатор; результат придёт отдельным финальным пакетом.

**Ошибки потока:**

- Отклонение **до** первого пакета (неверный ключ, нет прав, лимит, валидация) → обычный HTTP-статус + JSON `ErrorResponse`, поток не открывается.
- Ошибка **после** первого пакета → отдельный SSE-пакет `data: {"error": ..., "error_type": ...}`, HTTP-статус к этому моменту уже 200.

### 2.5. Контекст диалога

#### GET `/public/v1/conversations/{conversation_uuid}/context_tokens`

Query-параметр `branch` (опционально): по умолчанию `latest`; если указан `message_uuid` — учитывается ветка диалога до этого сообщения.

```json
{ "token_count": 1234, "max_context_length": 384000 }
```

Позволяет оценить заполненность контекста **до** отправки сообщения. При приближении к `max_context_length` срабатывает серверная авто-компактизация.

> Фактическое `max_context_length` на 25.11.2026 — **384000** (в примере документации было 128000). Значение может зависеть от тарифа/модели, поэтому читайте его из ответа, а не хардкодьте.

### 2.6. Бюджет и лимиты

#### GET `/public/v1/budget`

```json
{
  "limits": {
    "sliding_5h": {
      "used_percent": 42.5,
      "resets_at": "2026-08-25T16:00:00Z"
    },
    "weekly": {
      "used_percent": 18.0,
      "resets_at": "2026-08-27T16:00:00Z"
    }
  }
}
```

- Расход приводится к обезличенным учётным единицам; клиенту отдаётся **только процент**, абсолютные значения не публикуются.
- Если 5-часовое окно не началось или истекло: `resets_at = null`, `used_percent = 0`.
- При превышении лимита создание сообщения возвращает `402 budget_exceeded`.

## 3. Модели данных

### UserContent (`role: user`)

Упрощён до строки:

```json
"content": "Объясни, как работает эта функция"
```

### ClientTool

Полное описание инструмента, который предоставляет клиент:

```json
{
  "name": "get_weather",
  "description": "...",
  "parameters": { }
}
```

`parameters` — JSON Schema.

### ToolContent (`role: tool`)

Результат выполнения инструмента:

```json
{
  "content": "<result or comment>",
  "structured_content": {},
  "details": {},
  "tool_call_id": "call_abc",
  "status": "ok"
}
```

| Поле | Описание |
|---|---|
| `content` | опционально; `null` для `accepted`/`rejected` без комментария |
| `structured_content` | опционально, структурированные данные для рендеринга |
| `details` | опционально, дополнительные детали для рендеринга |
| `tool_call_id` | идентификатор вызова инструмента |
| `status` | `ok` \| `accepted` \| `rejected` \| `error` \| `timeout` \| `ignored` |

### AssistantMessageContent (финальный пакет)

```json
{
  "content": "Привет.",
  "reasoning_content": null,
  "tool_calls": [
    { "id": "call_abc", "function": { "name": "get_weather", "arguments": "{\"location\":\"...\"}" } }
  ]
}
```

### AssistantMessageContentDelta (промежуточные пакеты)

```json
{
  "content": "При",
  "reasoning_content": null,
  "tool_calls": [
    { "index": 0, "id": "call_abc", "function": { "name": null, "arguments": "{\"loc" } }
  ]
}
```

`arguments` в `tool_calls` — **строка** JSON, может быть невалидной посередине стриминга; клиент собирает её накоплением.

### ConversationMessage (в `GET /conversations/{uuid}`)

```json
{
  "uuid": "msg-2",
  "parent_uuid": "msg-1",
  "role": "assistant",
  "content": {},
  "create_time": "2026-08-25T10:00:01Z"
}
```

`content` — `AssistantMessageContent` | строка (user) | `ToolContent`.

### Правила статусов инструментов

- **Клиентские инструменты:** `ok` (с `content`), `rejected` (`content` опционально — комментарий), `error` (с `content`), `timeout` (с `content`), `ignored` (`content = null`).
- **Серверные инструменты (MCP/system):** `accepted` (`content = null`) или `rejected` (`content` опционально).

## 4. Ошибки

Единый формат:

```json
{
  "error": "...",
  "error_type": "validation"
}
```

| HTTP | `error_type` | Когда |
|---|---|---|
| 401 | `no_token` / `invalid_token` / `token_not_found` | Отсутствует или невалиден API-ключ |
| 402 | `budget_exceeded` | Исчерпан бюджетный лимит (5-часовое окно или неделя) |
| 402 | `no_active_tariff` | У токена нет активной опции и замена не найдена |
| 403 | `access_denied` / `user_conversation_conflict` | Нет доступа (в том числе к чужому диалогу) |
| 404 | `resource_not_found` | Диалог или сообщение не существует |
| 409 | `conflict` | Несовместимое состояние (например, генерация уже идёт) |
| 422 | `validation` | Ошибка валидации тела запроса или enum |
| 424 | `insufficient_context` | Недостаточно данных для генерации названия |
| 429 | `rate_limit_exceeded` | Превышен технический rate-limit |
| 500 | `internal` / `connection` / `database` / `llm` | Внутренняя ошибка; `llm` — недоступность LLM/зависимостей |

---

## 5. Типовой сценарий «с нуля»

1. `POST /public/v1/conversations` → получить `uuid` диалога.
2. `POST /public/v1/conversations/{uuid}/messages` с `role: user`, `Accept: text/event-stream` → читать дельты, собрать финальный `content`.
3. (опц.) `POST /public/v1/conversations/{uuid}/title` → название для списка диалогов.
4. Если пришёл `tool_calls` — выполнить инструмент локально и отправить `POST .../messages` с `role: tool`, `content: [ToolContent]`.
5. Перед длинной серией сообщений — `GET .../context_tokens`; при необходимости — `POST .../compact`.
6. Контроль расхода — `GET /public/v1/budget`.

## 6. Практические замечания

- **Лимиты не публикуются в штуках.** Планировать нагрузку можно только эмпирически, по `used_percent`: снимайте `budget` до и после типовой операции и получайте «стоимость» операции в процентах окна.
- **Ошибка `no_active_tariff`** означает, что ключ выпущен, но тариф не активирован/истёк — проверяйте подписку на портале ИТС.
- **`429` и `402` — разные вещи:** `429` — слишком часто (технический rate-limit), `402` — исчерпан объёмный лимит (5ч/неделя).
- **Компактизация необратима** для истории диалога: после сжатия старые сообщения в контексте уже не в полном виде. На коротком контексте `compact` — мгновенный no-op (`compact_finished` без изменений).
- **Диалог не блокируется на время генерации** (проверено 25.11.2026): параллельные `POST /messages` принимаются оба и создают ветки, `409 conflict` в этих сценариях не возникает. А поскольку `GET /conversations/{uuid}` отдаёт плоский список без ветвления, после параллельной отправки линейную историю по нему не восстановить — сериализуйте запросы на клиенте.
- **Бета:** состав полей, коды ошибок и тарифы могут меняться; в письме «1С» обещала отдельное уведомление об условиях после завершения беты.
