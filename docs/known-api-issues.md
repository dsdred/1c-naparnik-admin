# Известные проблемы публичного API «1С:Напарник разработчика»

Собрано при тестировании 25–26.11.2026 (базовый адрес `https://code.1c.ai/public/v1`,
статус — бета). Подробный протокол проверки: [API-test-report-2026-11-25.md](API-test-report-2026-11-25.md),
справочник по API: [1C-Naparnik-Public-API.md](1C-Naparnik-Public-API.md).

Часть пунктов обходится на стороне шлюза, часть — только обходится, но не лечится.

## 1. Параллельные сообщения не дают `409` — диалог ветвится

Документация описывает `409 conflict` как «генерация уже идёт», но воспроизвести не
удалось: два `POST /messages` с одним `parent_uuid` проходят оба, и в диалоге
появляются две ветки от одного родителя. `GET /conversations/{uuid}` отдаёт плоский
список сообщений без ветвления, поэтому линейную историю после этого восстановить
нельзя.

**Что делает шлюз:** сериализует запросы одной сессии — второй ждёт первого.

## 2. Черновики `content_delta` могут быть отфильтрованы или переписаны

В потоке ассистент приходит дельтами, затем финальным пакетом. Финальный `content`
приоритетнее: сервер вправе выбросить или поправить отправленное. Отозвать уже
отданную клиенту дельту протоколы OpenAI и Anthropic не позволяют.

**Что делает шлюз:** не транслирует `content_delta` клиенту, отдаёт только
подтверждённые пакеты. Цена — нет посимвольной «печати».

## 3. `role: tool` без реплики ассистента отклоняется

Если отправить сообщение с `role: tool` в диалог, где ещё нет реплики ассистента с
`tool_calls`, ответ — `422 validation`:

```
There are no assistant messages in the conversation history.
Tool responses can only be provided for existing tool calls.
```

Это всплывает при переносе истории в новый диалог (после rewind или потери привязки).

**Что делает шлюз:** при засеве нового диалога передаёт результаты инструментов
текстом пользователя.

## 4. `last_activity` в списке диалогов не обновляется

После нескольких сообщений поле осталось равным `create_time`. Сортировать список
диалогов по активности нельзя. Похоже на баг беты.

## 5. `PUT /conversations/{uuid}/title` возвращает `204`

Тела нет, в документации код ответа не указан. Клиенту не нужно парсить ответ —
достаточно проверить статус.

## 6. `422` отдаёт `error` массивом, а не строкой

```
{"error":[{"type":"literal_error","loc":["body","role"],"msg":"Input should be ..."}],
 "error_type":"validation"}
```

Формат `error` описан как «строка или объект» — фактически бывает и массив
(FastAPI/pydantic).

**Что делает шлюз:** разбирает все три формы и собирает читаемый текст.

## 7. `max_context_length` = 384000, а не 128000

В документации в примере 128000, фактически `GET /conversations/{uuid}/context_tokens`
и `details.max_context_length` в потоке отдают 384000. Значение отдаётся клиентам в
`naparnik_context` и `context_length` у `/v1/models`.

## 8. `compact` на малом контексте — мгновенный no-op

На диалоге ~6 тыс. токенов `POST /compact` сразу возвращает `compact_finished`,
ничего не сжимая. Полезный эффект ожидается только у порога контекста, поэтому
авто-компактизация шлюза на коротких диалогах не срабатывает.

## 9. `usage` в пакетах не документирован

Поле приходит в финальном пакете (`prompt_tokens`, `completion_tokens`,
`cached_tokens`, `reasoning_tokens`, `total_tokens`) и используется шлюзом для
`usage` в ответах клиентам. Документацией не описано — может измениться.

## 10. Транспортные обрывы без HTTP-ответа

Один из шести параллельных запросов curl получил обрыв без ответа (`000`) при
штатном прохождении остальных. Повторить не удалось. Вывод для клиента: нужен
ретрай на транспортные ошибки, а не только на 5xx.

## 11. Ошибки ключа приходят с разными кодами

Невалидный ключ даёт `401 token_not_found`, отсутствие заголовка — `401 no_token`.
Ориентироваться нужно на HTTP-статус 401, а не на конкретный `error_type`.

## 12. Кириллица из консоли Windows уходит в cp1251

`curl -d '…русский текст…'` в Git Bash/CMD отправляет тело в cp1251, и сервер
отвечает `400 There was an error parsing the body`. Используйте файл в UTF-8 и
`--data-binary @file.json`. Шлюз такие запросы отклоняет с подсказкой.
